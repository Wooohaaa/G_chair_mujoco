# 视频提取姿态 — 优化规划

> 基于 2026-11-22 的量化基线诊断和可行性实验。本文是**规划**，按优先级分阶段，
> 每阶段都有明确的验证方法。目标是把视觉方案从"能用"提升到"体感可用"。

---

## 0. 先认清天花板（避免无效投入）

从单目游戏画面恢复物理加速度是**病态问题**：无深度、镜头跟随、无真值。
即使全部优化做完，精度也达不到游戏遥测（RMS 1.5mm vs 视觉 5mm+）。
所以优化目标是：**体感上正确、方向对、不突兀**，而不是追求物理精确。

当前视觉方案是**降级/备用方案**（给没有遥测接口的游戏用），GTA5 优先用 mod 遥测。

---

## 1. 现状基线（量化诊断，2026-11-22）

### 1.1 视觉推导 vs 真实遥测的幅度对比

| 通道 | 真实 std | 视觉 std | 比值 | 判断 |
|---|---|---|---|---|
| accel_x (横向) | 0.135 | 0.356 | **2.6×** | 严重高估（镜头晃动混进来） |
| accel_z (纵向) | 0.156 | 0.236 | 1.5× | 偏高 |
| accel_y (垂直) | 0.135 | 0.122 | 0.9× | 幅度接近，但视觉缺碰撞尖峰（真实 -4.2G，视觉 -0.34G） |
| rot_x (roll) | 0.023 | 0.032 | 1.4× | 尚可 |
| **rot_y (yaw)** | **0.152** | **0.047** | **0.31×** | **严重不足——最大短板** |
| rot_z (pitch) | 0.013 | 0.016 | 1.2× | 但 47.5% 帧近零，信号稀疏 |

### 1.2 关键发现

- **yaw 提取方式错误**：当前 `rot_y = mean(fx) * 0.08`（路面横向光流均值），
  与真实偏航角速度相关性弱（std 只有真实 1/3）。
- **横向信号被污染**：`mean(fx)` 包含镜头随动/路面倾斜，高估 2.6 倍。
- **缺冲击动态**：`accel_y` 用光流幅值 `bump`，碰撞时路面纹理变化不一致，
  抓不到真实遥测里的 -4.2G 撞击尖峰。
- **无真值对齐**：视频 829s，抓的真实遥测 45s，不是同一段——无法做严格误差验证。
- **性能**：RK3566 上 13.7 FPS，光流占 97% 耗时；PC 上 97 FPS。

### 1.3 可行性实验（已做）

| 实验 | 结果 | 结论 |
|---|---|---|
| 光流旋度提 yaw（路面 ROI） | std 0.0038，93% 近零 | ❌ 路面无纹理，旋度失效 |
| 光流旋度提 yaw（远景 y<0.35H） | std 0.0127，14% 近零 | ✅ 远景建筑纹理丰富，可用 |
| 256×144 + 轻量光流参数 | PC 5.9ms/帧 | 板子可达 ~24 FPS |

**结论：yaw 应改用远景光流旋度，比当前方法强 3.4 倍。**

## 2. 优化方案（按优先级）

### 阶段 0：建立验证基础（必须最先做，否则无法判断改进是否有效）

**目标**：得到"同一段驾驶的视频 + 真实遥测"同步数据。

**做法**：
1. 在 RK3566 采集 HDMI 画面的同时，把游戏机发来的 UDP 遥测也带时间戳存盘
   （复用 `capture_raw.py`，但和视频采集同启同停）。
2. 对齐：视频帧号/fps ↔ 遥测 `time` 列。
3. 产出 `paired_video_telemetry/` 数据集，供后续所有 A/B 对比。

**验证**：能算出"视觉输出 vs 真实遥测"的相关系数和误差（这是唯一的优化标尺）。

---

### 阶段 1：算法改进（P0，收益最大）

#### 1.1 yaw：改用远景光流旋度 ✅ 已验证可行
```
当前: rot_y = mean(fx_路面) * 0.08
改为: rot_y = ω_远景,  ω = mean((rx*v - ry*u)/r²)  over 远景区域(y<0.35H)
```
- 远景区域建筑纹理丰富，旋度信号 std 0.0127（vs 路面 0.0038）
- 需标定增益：让视觉 rot_y std 接近真实 0.152
- 预期：yaw 从 0.31× 提升到 ~0.8×

#### 1.2 sway：用 FOE（膨胀中心）偏移替代 mean(fx)
```
当前: accel_x ← mean(fx_路面) * 0.8
改为: 计算光流场的 FOE（膨胀中心），FOE 相对画面中心的水平偏移 ↔ 横向运动
      accel_x ← FOE_x_offset * 增益
```
- FOE 是更物理正确的横向运动指标，且对镜头俯仰不敏感
- 同时把增益降到当前的 ~1/2.6，消除 2.6× 高估

#### 1.3 heave/冲击：用光流幅值的时间变化率
```
当前: accel_y ← (bump - 2.0) * 0.08  (bump = 光流幅值 p75，静态)
改为: 检测全画面光流幅值的突变 |d|flow|/dt| → 冲击事件
      accel_y ← 平滑的路面颠簸 + 冲击脉冲
```
- 能抓到碰撞/减速带（真实遥测有 -4.2G，当前视觉只有 -0.34G）

#### 1.4 场景门控（用简单方法，不用 YOLO）
- 检测画面方差/边缘密度：菜单/加载画面纹理少 → 抑制输出
- 省下 YOLO 的 50~80ms/帧开销

#### 1.5 光照鲁棒
- 加 CLAHE（对比度受限直方图均衡）或改用梯度域光流
- 隧道进出、昼夜切换时光流更稳

### 阶段 2：性能优化（P1）

| 方案 | 预期帧率(RK3566) | 代价 |
|---|---|---|
| 当前 320×180 + Farneback | 13.7 FPS | 基线 |
| **256×144 + levels=2,win=11,it=1** | ~24 FPS | 光流精度略降，需重标定 |
| 再降到 160×90 | ~40+ FPS | 远景纹理丢失，yaw 变差 |
| Lucas-Kanade 稀疏光流 + 角点 | 待测 | 路面角点少，可能不稳 |

**建议**：先做 256×144 + 轻量参数（已验证可行），保住远景区域分辨率以维持 yaw。
分层方案：全画面低分辨率算 yaw/sway，ROI 稍高分辨率算 heave。

---

### 阶段 3：架构修正（P1，解决双重滤波）

**问题**：视觉节点已对 accel 做了低通+洗出，发出的 25 通道进 `motion_pipeline` 后
又被映射+洗出一次——**双重洗出**会加速信号衰减。

**两个方案**：
- A. 视觉节点直接输出 **6DOF 位姿或缸位移**，跳过 motion_pipeline 的映射
  （需新增一路"视觉直连"模式，改动小）
- B. 视觉节点输出**原始加速度**（不洗出），让 motion_pipeline 统一做一次滤波
  （改动更小，但视觉侧的 p75 尖峰要保留给下游处理）

**建议 B**：视觉侧只做表征提取和轻度平滑，把洗出/限速统一交给 motion_pipeline，
保持"一个数据链"的设计。

---

### 阶段 4：YOLO 语义（P2，可选，最后做）

当前 `YoloGate` 是 TODO stub。补 RKNN INT8 后处理，用于：
- 前方车辆检测 → 距离突变产生冲击（补 heave）
- 场景识别（高速/城市/隧道）→ 切换增益档位

**前提**：阶段 1~3 做完且验证有效后再加，否则增加 50~80ms/帧拖慢帧率，
收益不明确。

## 4. 风险与取舍

1. **没有真值就无法优化**——阶段 0 不能跳过，否则阶段 1 的效果无法量化。
2. **远景旋度依赖建筑纹理**——在旷野/高速场景可能失效，需要 fallback 到当前方法。
3. **FOE 计算复杂度**——需要最小二乘拟合，可能吃掉性能收益；可先用简化版
   （光流加权质心）验证方向。
4. **视觉精度天花板低**——优化到体感可用即可，不要投入过多追求精确。
